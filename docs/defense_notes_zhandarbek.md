## Вопросы и ответы

**Почему разбиение хронологическое, а не случайное?**
Модель будет оценивать будущие транзакции. Случайное разбиение даёт модели «подглядеть» в будущее и встретить почти такие же транзакции (в данных есть дубликаты) и завышает метрики. Мошенничество ещё и меняется со временем.

**Что значит «граница не разделяет одинаковый Time»?**
Несколько транзакций имеют одну и ту же секунду. Если разрезать ровно по номеру строки, одна секунда может оказаться и в validation, и в test. Я сдвигаю границу к следующему различному значению `Time` (`find_cut_positions`, `np.searchsorted(..., side="right")`).

**Что такое `transaction_id` и почему он стабильный?**
Позиция строки в исходном CSV (с нуля). Файл уже отсортирован по времени (аудит это проверяет), значит, id ещё и хронологический номер. Пока используется тот же файл, id не меняется. SHA-256 файла записан в `data_audit.json`.

**Почему не удалили дубликаты?**
Это изменило бы размер датасета и id, о которых договорилась вся команда. Дубликаты посчитаны аудитом и SQL-запросом `q12`; как с ними обходиться в обучении, решает ML-модуль (Диас).

**Почему V1–V28 в `float32`, а `Amount` в `float64`?**
`float32` даёт относительную ошибку порядка 1e-7: для PCA-признаков это не важно, а память вдвое меньше. `Amount` это деньги: суммы в SQL должны совпадать с CSV. Каждое приведение типа проверяется (`optimize_dtypes`): целые значения, диапазон, допустимая ошибка; иначе исключение.

**Почему Parquet?**
Колоночный формат: меньше размер файла, сохраняются типы, можно читать только нужные колонки и фильтровать по `split`. В бенчмарке видно, что время чтения мало отличается (парсер CSV в pandas быстрый), выигрыш в размере, памяти и проекции колонок.

**Зачем чанковая загрузка, если файл маленький?**
Требование курса для наборов от 200 МБ; наша тема в списке исключений по объёму, но я реализовал и измерил. Чанковая загрузка медленнее, зато пиковая память ниже (см. таблицу в отчёте). Результат идентичен обычной загрузке, это проверяется тестом.

**Что такое нормализованная схема и почему так?**
Повторяющийся текст (название сплита, метка класса) хранится один раз и подключается по внешнему ключу. Факт-таблица `transactions` узкая, 28 признаков вынесены в таблицу 1:1 `transaction_features`: аналитические запросы не читают лишние колонки. `amount_bands` подключается по диапазону (`amount >= lower_bound AND amount < upper_bound`), а не по ключу.

**Почему `time_slots` не содержит «час суток»?**
В данных нет абсолютного времени: `Time` это секунды от первой транзакции. Поэтому есть `hour_index`, `day_index` и `hour_in_cycle` (индекс часа по модулю 24), без утверждений про время суток.

**Как гарантируется целостность базы?**
Первичные и внешние ключи (`PRAGMA foreign_keys = ON`), `NOT NULL`, `UNIQUE`, `CHECK`, `ON DELETE CASCADE`. При сборке база строится во временном файле и проверяется: число строк, сумма `Amount`, число фродов по сплитам, `foreign_key_check`, `integrity_check`; только потом перемещается на место.

**Чем CTE отличается от подзапроса?**
CTE (`WITH ... AS`) именованный временный результат, читается сверху вниз и может использоваться несколько раз. Подзапрос вложен в выражение (`q04`: сравнение со скалярным подзапросом; `q11`: `NOT EXISTS`). Оба есть в моих запросах.

**Что делает оконная функция? Чем отличается от GROUP BY?**
GROUP BY схлопывает строки в одну на группу, оконная функция считает по «окну» строк, не схлопывая: `LAG` (предыдущая строка, `q05`, `q08`), `RANK` и накопительный `SUM OVER` (`q06`), `NTILE(10)` (децили, `q07`), `ROW_NUMBER` с `PARTITION BY` (`q09`).

**Что делает HAVING и чем отличается от WHERE?**
`WHERE` фильтрует строки до группировки, `HAVING` группы после агрегации. В `q03` HAVING отбрасывает часы с малым трафиком, где доля фрода шумная.

**Почему Pandas оказался быстрее SQLite?**
Данные помещаются в память, Pandas работает векторизованно по колонкам Parquet, а SQLite читает строки и проходит через SQLAlchemy. Ответы совпадают (бенчмарк прерывается, если нет). Ценность SQL здесь не в скорости: целостность, индексы, декларативность и возможность соединять предсказания модели с транзакциями.

**Как вы проверили, что SQL считает правильно?**
Восемь запросов пересчитаны в Pandas независимо (`src/db/crosscheck.py`) и сравнены; например, число дубликатов из SQL равно числу из аудита исходного CSV. Пайплайн останавливается, если что-то не совпало.

**Как избежали утечки данных в EDA?**
Всё, что связывает признаки с целевой переменной (корреляции, `Amount` по классам, дискриминативные признаки), считается только на train. Описательные факты (баланс классов, профиль по времени) используют все строки.

**Что ограничивает выводы?**
В validation и test мало фродов (числа в отчёте), поэтому метрики там шумные; признаки анонимизированы, поэтому EDA показывает *что* разделяет классы, но не *почему*; бенчмарки измерены на одной машине; файл взят с публичного зеркала (SHA-256 записан).

**Что вы не делали и почему?**
Не обучал модели, не подбирал порог и не считал метрики качества: это работа Диаса и Адама. Я подготовил для них данные, разбиение, API и (как предложение) таблицы для результатов экспериментов.
